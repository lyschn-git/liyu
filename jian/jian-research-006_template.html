鉴 · AI协作思行录

和AI协作一个月，
我总结了7条最核心的经验

2026年6月19日

经验之谈

备注： 本文所指的"AI"不是豆包、元宝、DeepSeek这类聊天大模型，而是具备Agent能力的协作工具——如扣子（Coze）、WorkBuddy、EasyClaw等。

01. 每次交付，都要有一个"锚点"

一次真实的教训：开发中途上下文耗尽，对话中断，所有改动丢失。AI不记得之前说过什么，一切从零开始。上下文断了，记忆就断了。记忆断了，一切从零。

那次之后，我学到一个词：锚点。

锚点是什么？是一个确定的交付物，一个可以被验证的版本，一个所有后续工作的起点。它可能是一个压缩包、一份文档、一个截图确认——不管是什么形式，关键是：有了它，我们从同一个地方出发；没有它，我们从各自的记忆出发。

锚点不只适用于代码。 写文章、做设计、定方案——任何需要多轮迭代的工作，都需要锚点。没有锚点，每一轮对话都在重新对齐；有了锚点，每一轮对话都在推进。

02. 一次只改一件事，小步快跑

开球v7的真实节奏：先修一个问题，测试；发现下一个，再修，再测试。每一步改动不超过两三个文件，每一步交付都有完整的验证记录。

小步快跑的节奏

改一点 → 测试 → 确认 → 下一件

改一点 → 测试 → 确认 → 下一件

……

这不是慢，这是可靠的快。

小步快跑的本质是把问题暴露在水面，不让它沉到水底。改了一大堆，测出问题，不知道是哪改出来的。改一点测一点，出问题，一眼就知道原因。

03. 给AI反馈，要给数据，不给感受

无效反馈："感觉不太对"

有效反馈："这里球员名字显示为空，预期应该显示张三、李四"

有效反馈公式

出了问题 → 指出具体位置 → 说明预期结果 → 提供复现手段（截图/日志）

AI擅长处理信息，不擅长猜测感受。 模糊的感受是协作中最大的消耗，清晰的数据是协作中最好的推进剂。

04. 要求AI说"我不确定"

开发中出现过一个现象：AI说"已修复"，但实际没有修复；或者说"这个逻辑没问题"，但其实有问题。

这是AI的常见毛病：在不确定的时候，倾向于给一个听起来确定的回答，而不是说"我不确定，需要更多信息"。

不确定性协议

明确要求AI在以下情况主动报告：

• 涉及外部系统或API时

• 涉及用户数据或隐私时

• 改动影响范围不明确时

• AI自己对结论没把握时

模糊的确定性是协作中最大的风险。要求AI报告不确定性，是对自己的保护。

05. 口头确认不算交付

代码改完了，不算交付。口头说"已修复"，不算交付。

真正的交付：打包好了，验证通过了，锚点版本成立了。

"已修复"是声明，"已修复且验证通过"才是结论。信任验证，不信任声明。

06. 灵感闪现时，立刻形成节点性记录

跟AI协作，特别是创作性的协作，灵感往往是稍纵即逝的。

AI对话有上下文长度限制。聊到一定长度，新内容会把旧内容挤出去。这是技术现实。

所以，在灵感闪现的那一刻，就要立刻形成节点性的记录。 不是等聊完再整理，是边聊边保存。哪怕是一句话、一个关键词、一张截图，先记下来。

一闪而过就找不到了。特别可惜。

07. 识别关键信息，遵守协作规则

还有一条教训，值得单独记一笔。

有时候，用户会明确说出验收标准："按之前交付的标准一次性完整交付"。这是一个关键信号——意味着这次有明确的具体要求，不是泛泛的常规任务。

识别关键信息的5条判断依据

1. 用户重复之前说过的标准 → 这是已经在册的规则，不是建议

2. "不要"、"必须"、"按XX标准" → 明确约束，不是可选项

3. 用户已说出验收条件 → 把"什么算完成"讲清楚了

4. 语气越正式，权重越高

5. 用户说"有中间产物够用了" → 这是把过程当结果

核心问题：把"有中间产物"当成了"够用的版本"，把"转出HTML"当成了"完成"，没有把"网页能看"当成验收标准。

可靠是底线，不是加分项。做不到可靠，就是不合格。

锚点是外部记忆，不依赖AI的上下文。

小步快跑是可靠的快，不让问题沉到水底。

数据比感受有效，不确定性要主动报告。

交付物是唯一的事实。口头确认不算交付。可靠是底线，不是加分项。
